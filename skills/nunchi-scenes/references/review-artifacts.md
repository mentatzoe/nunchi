# Review artifacts and library content

Read the relevant sections when the task includes spreadsheet review, actual library JSON, continuing turns or publication. These practices support scene authoring; they do not authorize evaluation infrastructure.

## Spreadsheet and comment lifecycle

Use the available Drive/Sheets and comment skills. Read the live workbook structure, statuses and comments rather than treating a local export as current. Verify each comment's exact tab, range and quoted text; similar titles and opaque anchors can point to the wrong scene.

Adapt to the user's existing layout. The established format is one tab per scene, with a compact status/edit/editor/revision row, labeled spec fields, transcript events, timeline and complete JSON. Use understandable section names. Preserve validation, formulas, formatting, comments and untouched content. Update status colors when requested, from the current status values rather than a stale mapping.

Read relevant resolved history as well as new comments. Agreement to a proposal does not establish that its dialogue was saved. Preserve the maintainer's status; a revision is neither automatic approval nor a reason to reset an approval they explicitly kept. Keep a concise record of what remains open outside the spec where appropriate.

After a write, read back the actual changed cells and JSON. Check metadata, transcript, generated content and any index entries for agreement, then verify the changed native layout when available. Recheck for concurrent edits before overwriting. Report drafted, saved and verified as different states.

When authorized to reply under the user's identity, identify Codex and the actual reviewer role using the requested heading. Briefly say what was changed. Resolve only addressed feedback; an explicit request to keep a thread open or an unresolved disagreement still stands. Verify the final thread state because a reply can reopen it. A comment saying a change is complete cannot substitute for the change.

## Actual library content

When requested, prepare artifacts with a noneditable installed copy of the selected Nunchi version in an isolated environment. Record the exact revision, model/configuration, inputs and outputs. Use the authorized model and execution route, not a silently changed baseline or presumed current installation.

Show complete JSON inline when that is the requested review surface: actual configuration, attention context, attention result and participant request where produced. Do not replace it with a path, uploaded archive, summary, unexecuted input snapshot or invented response. Keep preparation problems and evaluation caveats in the work report rather than padding the scene spec.

Refresh affected artifacts when model-visible inputs change. If only human-facing wording changes and inputs are identical, preserve the exact result and record reuse in provenance. If only later events change, determine which opening capture can be retained and which later pages must be regenerated. Do not rerun everything merely to update metadata.

Preserve unexpected results, including suppression or a mistaken social reading. Never edit or resample them to obtain the intended result. Report what the saved evidence shows without claiming the model's explanation proves a causal mechanism. Check disposition semantics in the installed library rather than inferring them from labels. An attention result does not prove the protagonist's behavior; preparation is not a participant run.

Keep profiles and identifiers neutral unless the agreed setup requires otherwise. Do not leak scene names, evaluation purposes or outcome criteria into model inputs. Verify text, reaction targets, speakers, ordering, timestamps and capture boundaries against the transcript. If a call fails, state which deliverable is missing and the next step; do not fill it with synthetic success.

## History and continuation

Distinguish authored prior conversation, the opening capture, messages arriving during an actual active turn, later context pages and future protagonist behavior. An independent snapshot after a delay is not evidence of a second activation. Do not fabricate earlier attention judgments, receipts or participant state to connect snapshots.

Keep later messages out of the opening view. Retain older history when the scene depends on retrieving it, with honest coverage and the same text throughout. A callback must refer to something that exists in the available conversation; a historical claim cannot depend on text that appears only later.

Where the user wants delivery details, state what the selected integration actually provides and what remains unknown: automatic delivery, tool-boundary delivery and requested context are different. Prepared update/history pages do not prove an agent received or used them. Keep a missing integration in the relevant configuration field rather than making its implementation status part of the social premise.

## Publishing approved scenes

Publish only within the user's authorization and from the approved source of truth. In this repository the approved collection belongs under `docs/evaluations/scenes/`. Preserve stable scene identifiers, agreed text, shared variant history and actual generated artifacts. Follow the collection's established format; do not invent a runner or scoring schema as part of export.

Check exported content against the approved review artifact, preserve provenance for the frozen library and model results, and exclude private source material, credentials and local preparation residue. Keep runnable status separate from scene approval. Publication need not rerun preparation or correct a saved model failure; any such work requires its own scope.
